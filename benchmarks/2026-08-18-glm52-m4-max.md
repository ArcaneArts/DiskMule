# GLM-5.2 full-checkpoint out-of-core oracle — 2026-08-18

This record is a local correctness and bounded-residency observation, not a
universal performance claim. Filesystem cache state, background memory use,
power, and thermals were not controlled closely enough to label any run cold.

## Conditions

- DiskMule runtime commit: `e2de82cd6f721f2353ff6e06f1292bedc377282d`
- Hardware: MacBook Pro `Mac16,6`, Apple M4 Max, 16 CPU cores, 128 GB unified
  memory
- OS: macOS 26.5.1 (`25F80`)
- Model: `mastouri/GLM-5.2-colibri-int4-g64-with-int8-mtp`, revision
  `fd9b461ac7cae4b921470d0db12230c6505bd03c`
- Ordinary container: 141 grouped-INT4/gs64 safetensors shards,
  419,296,541,560 bytes; the optional 9,959,321,520-byte MTP shard was present
  but ordinary decoding did not load it
- Complete snapshot contract: 142 shards, 118,478 unique tensors, 78 ordinary
  layers, 75 sparse layers, 256 routed experts per sparse layer, no DSA
  indexer sidecar
- Backend: retained read-only sharded mappings for dense weights; Metal
  grouped-INT4 execution; exact selected experts loaded by bounded positional
  reads into a deterministic per-layer LRU
- Prompt text:
  `[gMASK]<sop><|user|>Hi<|assistant|><think></think>`
- Prompt IDs: `154822, 154824, 154827, 13041, 154828, 154841, 154842`
- Context: 64 tokens; greedy/temperature zero; MTP disabled
- Build: Cargo release profile
- Main oracle command:

```bash
DISKMULE_GLM52_SNAPSHOT=/path/to/glm52_i4 \
DISKMULE_GLM_EXPERT_SLOTS=1 \
DISKMULE_GLM_DIRECT=1 \
cargo test --release --test glm52_reference \
  forced_streaming_metal_decode_matches_the_colibri_oracle \
  -- --ignored --nocapture
```

The full checkpoint is about 400 GiB and its approximately 370 GB routed
expert pool cannot fit in 128 GB unified memory. One slot per sparse layer
retained 1,592,524,800 expert bytes, less than 0.5% of that pool. The process
therefore executed genuinely out of core rather than relying on implicit full
model residency.

## Authoritative Colibri oracle

Colibri commit `4ef9a9920dd4290b4ac26f74e73913fd18379bc9` was built in an
isolated temporary copy with `ARCH=native`. Its CPU ordinary-decode run used
the same checkpoint, prompt, 64-token context, greedy selection, MTP off, one
expert slot, a 24 GB RAM budget, and automatic cap raising disabled.

It produced the four greedy IDs:

```text
13041, 0, 358, 2776
```

Decoded text was `Hi! I'm`. Colibri reported 33.11 s for the seven-token
prefill and 17.17 s for four generated tokens, 37.584 GB fetched during decode,
about 12.39 GB RSS, a 14.40 GB peak footprint, and zero process swaps. Colibri
rewrote its `.coli_usage` telemetry sidecar despite usage saving being
disabled; DiskMule retained that diagnostic copy in temporary storage and
restored the model's original 90,160-byte sidecar byte-for-byte. No tensor
shard changed.

## DiskMule correctness result

The one-slot direct-I/O run produced exactly the same IDs and decoded text:

```text
13041, 0, 358, 2776  ->  Hi! I'm
```

The test also required nonzero cache misses, evictions, positional reads,
bytes read, resident expert bytes, mapped dense bytes, and KV bytes. This is an
exact token-level cross-runtime oracle, not a plausible-text check. Tiny
fixtures separately retain the declared `1e-4` CPU/Metal and streamed/resident
numeric tolerance.

## Buffered I/O and cache-budget sweep

The one-token runs held the prompt, backend, context, sampling, and checkpoint
fixed. They were sequential first-observed measurements; OS caches were not
purged, so run ordering is a material caveat.

| Attention time | included in four-token aggregate | 432.080 s | 450.101 s |

| Process swaps | 0 | 0 | 0 |

Buffered one-slot mode was 6.2% faster than the preceding direct observation,
but direct expert I/O wait per forward was slightly lower. That disagreement,
plus uncontrolled cache and thermal state, is why the result does not justify
a general buffered-versus-direct claim.

Eight slots yielded a 19.4% hit rate and reduced misses and explicit bytes by
19.4%, while TTFT became 4.9% slower than buffered one-slot mode. Attention,
not expert I/O, dominated both runs. The larger cache behaved exactly as
bounded: observed RSS rose by about 11.1 GB alongside the 11.15 GB increase in
logical slot residency. System pressure remained at least 80% free, no
throttled pages appeared, and system swap usage declined across both buffered
runs. Existing system swap and compressor occupancy predated the tests.

The planned approximately 96 GB cache point was intentionally not attempted
on this already busy host. It would add risk without evidence of a wall-time
benefit for this prompt. Larger-budget and queue-depth experiments should wait
for an isolated session and an optimized/DSA attention path.

## Kernel A/B and remaining performance limitation

Before the 256-lane grouped-INT4 row reduction, a direct one-token CLI run took
504.66 s wall time, peaked at 1.93 GB RSS, and selected `13041`. With the new
kernel, direct time to the same first token was 492.49 s, a first-observed 2.4%
improvement, and the four-token oracle remained exact. The modest end-to-end
change is consistent with the final profile: grouped expert work is no longer
the limiting phase, while dense exact attention still is.

DiskMule now meets the Phase 6 correctness and out-of-core residency contract.
It does not claim Colibri-class GLM throughput. The next performance work is
an absorbed/fused MLA decode path or a compatible complete DSA sidecar, followed
by isolated cold/warm and larger-cache sweeps.
